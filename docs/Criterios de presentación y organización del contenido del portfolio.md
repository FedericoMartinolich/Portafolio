# Criterios de presentación y organización del contenido del portfolio

## Objetivo

Realizar pequeños ajustes en el portfolio para mejorar la **jerarquía visual, legibilidad y cantidad de información presentada**, sin modificar innecesariamente el diseño general ni la identidad visual existente.

El objetivo principal es que el portfolio transmita profesionalismo y experiencia técnica sin sentirse sobrecargado, especialmente en las secciones de proyectos y experiencia.

La información debe estar organizada para que un visitante pueda:

1. Entender rápidamente qué es cada proyecto.
2. Identificar qué participación tuvo Federico.
3. Conocer las tecnologías y aspectos técnicos relevantes.
4. Ver el resultado o valor aportado.
5. Profundizar únicamente si el proyecto le interesa.

No se busca eliminar información importante, sino **reducir la cantidad de información visible simultáneamente y mejorar su jerarquía**.

---

# 1. Proyectos

Los proyectos son una de las partes más importantes del portfolio y deben ser fáciles de recorrer visualmente.

Cada proyecto debe comunicar rápidamente cuatro aspectos principales:

### 1. Qué es y qué problema resuelve

Explicar brevemente qué es el proyecto y cuál era la necesidad que buscaba resolver.

Debe ser una descripción de aproximadamente **1 o 2 frases**, evitando explicaciones extensas.

Cuando sea posible, combinar contexto y problema en una misma descripción.

Ejemplo:

> Plataforma web desarrollada para centralizar la gestión de productos, clientes y pedidos de un distribuidor mayorista, reemplazando procesos que anteriormente se realizaban de forma manual.

No es necesario separar siempre en bloques independientes llamados "Contexto", "Problema" y "Solución". Si la información puede expresarse naturalmente en un único párrafo breve, hacerlo de esa manera.

---

### 2. Participación de Federico

Esta debe ser una de las partes más importantes de cada proyecto.

Debe quedar claro **qué hizo concretamente Federico**, especialmente cuando el proyecto fue realizado dentro de una empresa o junto con otras personas.

Evitar frases genéricas como:

> "Desarrollé un sistema completo."

Preferir descripciones concretas:

> Participé en el desarrollo del backend y frontend, implementación de APIs, gestión de permisos y funcionalidades administrativas.

La información debe centrarse en las responsabilidades reales y relevantes, sin convertir esta sección en una lista extensa de tareas.

---

### 3. Tecnologías y aspectos técnicos

La información tecnológica ya cuenta con una sección general de Stack en el portfolio, por lo que **no es necesario repetir listas extensas de tecnologías dentro de cada proyecto**.

Dentro del proyecto solamente deben aparecer las tecnologías que sean relevantes para comprender cómo fue construido y, cuando corresponda, aspectos técnicos importantes.

Ejemplo:

> Laravel · Vue.js · MySQL  
> API REST · Roles y permisos · Arquitectura multiempresa

Evitar listas excesivamente largas de tecnologías si no aportan información significativa.

---

### 4. Resultado / impacto

Siempre que exista información suficiente, explicar brevemente cuál fue el resultado o qué aportó el proyecto.

Debe responder:

> ¿Qué mejoró o permitió conseguir este proyecto?

Ejemplo:

> Se centralizó la gestión comercial y se redujeron tareas que anteriormente se realizaban de forma manual.

No es necesario inventar métricas o resultados cuantificables si no existen.

Si no hay información concreta sobre impacto, puede utilizarse una descripción breve del objetivo alcanzado.

---

# 2. Estructura recomendada para el detalle de cada proyecto

El contenido de cada proyecto debería seguir, de manera flexible, esta jerarquía:

**Título del proyecto**

**Descripción breve**  
Qué es + qué necesidad resuelve.

**Mi participación**  
Qué hizo Federico.

**Tecnologías / aspectos técnicos relevantes**  
Solo lo necesario.

**Resultado**  
Qué aportó o qué se consiguió.

Esta estructura reemplaza la necesidad de tener numerosas secciones independientes como:

- Contexto
- Problema
- Objetivo
- Metodología
- Solución
- Mi participación
- Tecnologías
- Arquitectura
- Resultado
- Conclusiones

No se debe eliminar información relevante existente automáticamente, pero sí **agruparla y condensarla** cuando varias secciones estén comunicando prácticamente lo mismo.

---

# 3. Cantidad de información

La prioridad es que cada proyecto pueda entenderse rápidamente.

Evitar párrafos largos y bloques de texto consecutivos.

Como regla general:

- Descripción inicial: 1–2 frases.
- Participación: 1 pequeño párrafo o una lista corta.
- Tecnologías: lista breve.
- Resultado: 1–2 frases.
- Detalles adicionales: solamente cuando aporten verdadero valor.

La información debe poder recorrerse visualmente sin generar sensación de "documentación técnica".

El usuario que quiera conocer el proyecto en profundidad puede hacerlo, pero la primera lectura debe ser rápida.

---

# 4. Uso de jerarquía visual

No todas las partes de la información tienen que tener el mismo peso visual.

Dar mayor protagonismo a:

**Proyecto → Qué es → Mi participación → Resultado**

Los detalles secundarios deben ocupar menos espacio visual.

Utilizar adecuadamente:

- títulos
- subtítulos
- textos destacados
- listas cortas
- espacios en blanco
- separación entre bloques

Evitar que todo el contenido parezca tener la misma importancia.

El diseño debe sentirse **limpio, profesional y fácil de escanear**.

---

# 5. Experiencia profesional

La experiencia profesional debe ser mucho más resumida que una documentación de los trabajos realizados.

Cada experiencia debería mostrar rápidamente:

**Empresa**  
**Cargo / rol**  
**Período**

Y una descripción breve de aproximadamente 2–3 líneas que explique el tipo de trabajo realizado.

Después pueden aparecer algunos proyectos o responsabilidades relevantes, pero evitando enumerar absolutamente todas las tareas realizadas.

El objetivo es que alguien pueda comprender la experiencia profesional en aproximadamente **30 segundos**.

Los proyectos concretos pueden contener el detalle adicional.

---

# 6. Relación entre Experiencia y Proyectos

Evitar repetir exactamente la misma información en ambas secciones.

La sección **Experiencia** debe responder:

> ¿Dónde trabajó Federico y qué tipo de trabajo realizó?

La sección **Proyectos** debe responder:

> ¿Qué sistemas o trabajos concretos realizó y cuál fue su participación?

Si un proyecto ya explica detalladamente una determinada tarea, la experiencia laboral puede mencionarla de forma mucho más resumida.

Esto permitirá reducir considerablemente la sensación de contenido repetido.

---

# 7. Sección "Sobre mí"

La sección Sobre mí debe ser breve y funcionar como una presentación profesional.

Debe comunicar:

- Formación.
- Perfil profesional.
- Áreas de interés.
- Principales áreas de desarrollo.

No debe convertirse en una autobiografía ni repetir toda la información de Experiencia.

El texto debería poder leerse rápidamente y complementar, no duplicar, el resto del portfolio.

---

# 8. Principio general de diseño del contenido

El portfolio no debe intentar mostrar **todo lo que Federico sabe hacer de una sola vez**.

Debe funcionar mediante niveles de profundidad:

### Nivel 1 — Vista rápida

El visitante entiende quién es Federico y qué proyectos tiene.

### Nivel 2 — Interés

El visitante puede conocer brevemente qué hace cada proyecto y cuál fue la participación de Federico.

### Nivel 3 — Profundización

Si un proyecto resulta interesante, puede acceder a información técnica y visual adicional.

Por lo tanto, **la información detallada no debe desaparecer, sino estar mejor distribuida**.

---

# 9. Qué evitar

Evitar especialmente:

- Párrafos demasiado extensos.
- Muchas secciones pequeñas dentro de un mismo proyecto.
- Repetición de contexto, problema y objetivo.
- Repetición de las mismas tecnologías en múltiples lugares.
- Listas excesivamente largas de responsabilidades.
- Explicaciones técnicas que no aporten valor para comprender el proyecto.
- Bloques de texto con igual peso visual.
- Mostrar toda la información disponible simplemente porque existe.
- Convertir el portfolio en una documentación técnica.

El portfolio debe demostrar experiencia y capacidad técnica **sin exigirle al visitante leer demasiado**.

---

# 10. Criterio final

Antes de agregar o mantener información en una sección, evaluar:

> **¿Esta información ayuda a entender el proyecto, demuestra qué hizo Federico o aporta contexto relevante?**

Si la respuesta es no, debería eliminarse, resumirse o trasladarse a un lugar menos protagonista.

La prioridad debe ser:

**Claridad → Jerarquía → Brevedad → Profundidad opcional**

No modificar innecesariamente el diseño visual existente. Los cambios deben ser principalmente de **organización, jerarquía y cantidad de contenido**, manteniendo la identidad visual actual del portfolio y realizando solamente los ajustes de UI necesarios para que esta nueva estructura se vea natural y equilibrada.
